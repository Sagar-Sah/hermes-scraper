## Dependency comparisons

`crawler.route_dependencies` preserves full method/path/params/body/context. Its required context fields are `origin`, `session_scope`, `source_epoch`, `store_type`, `currency` and `service_signature`. Use opaque identifiers; do not place cookies, passwords or API credentials in this context. Unknown supplied context dimensions remain part of the key.

- `plan_dependency_probes(baseline, dimension, observed_values, ...)` plans one-axis comparisons for explicitly supplied discovered values. Changing a context field in a manifest is not proof that the supplier actually observed that state; the executor must establish it normally and retain evidence.
- `compare_probe_observations(observations, dimension)` compares successful complete response bodies only. Each observation supplies `request`, `status`, `data`, `response_id` and `complete=True`. Changed other fields are confounding; changed content is a dependency; inconsistent identical requests are unstable.
- A certificate covers only the exact tested request identity hashes. `finite_equivalence_key(request, certificate)` can alias those members. It does not remove a dimension, extend to untested values, combine separate certificates into an untested Cartesian product, or authorize reuse beyond the source freshness epoch.
- Historical URL/body repetition is insufficient to create these certificates because the old response table lacks full method/payload/session/service context. **No live dependency certificate was generated by this offline work.**

`validate_unique_lookup(observation)` requires the source-confirmed selector fields and one complete successful base-ID result. `plan_exact_quote_requests(lookup, operations, context=..., discovery_complete=True, catalog_option_ids=...)` emits only explicit GET price-table operations bound to that lookup and known option record IDs. Price probes require the same gates. The functions do not invent quantities, finishing fees, service defaults, shipping, production formulas or table composition.

## Queue integration contract

`HarvestQueue(store)` creates three new tables with `ensure_tables(store.engine)`: immutable scoped manifests, per-run shared tasks and product/scope consumers. It does not modify the existing store or engine.

```python
queue = HarvestQueue(store)
queue.install_manifest(run_id, product_id, scope, quote_manifest,
    certificates=(), max_attempts=3)
preflight = queue.preflight(run_id, measured_rps=measured_source_rate)
result = await execute_worker(queue, run_id, worker_owner, transport_factory,
    max_tasks=10, lease_seconds=60)
```

A manifest must be phase `QUOTE`, explicitly have completed discovery, and include validated lookup evidence for every operation. A scope binds the caller's run/product/filter/adapter contract. Reusing the same scope with changed task membership is rejected. A new scope retires the previous product scope. Exact request identities are shared across consumers; finite certificates can share only their tested members. Each consumer retains every original member request and lookup evidence, even when requests share one response.

`preflight` reports exact unique manifest tasks, active tasks, suspended tasks, pending/in-flight/succeeded/failed counts and remaining requests divided by the supplied measured requests per second. These estimates exclude future retries, retry waits, processing, export and undiscovered work. They are **not end-to-end completion estimates**. An inactive or failed queue cannot appear request-complete merely because nothing is currently claimable.

`execute_worker` accepts a caller-supplied transport factory. It may return a transport, an awaitable transport, or an async context manager. Bare transports are closed after each invocation; context managers control their lifetime. The helper calls `Transport.fetch` with the full leased context, renews leases while waiting, persists a `ResponseObservation` of kind `harvest` with the full request identity, then commits the response ID. Completion requires that binding plus exact origin/path/query, HTTP 200 and any certificate's unchanged semantic content.

The existing transport remains responsible for source pacing, authentication and HTTP retries. Queue attempts count **logical Transport.fetch invocations**, not lower-level network attempts. Queue retries retain the same manifest/task identity and have a bounded attempt budget. Only known transient network/rate/unavailable codes retry; authentication and integrity failures become terminal. Pausing the only active consumer stops lease renewal and cancels the in-flight fetch. A completed response may still be checkpointed after pause; it cannot be delivered until the intended product scope is active again.

`ready_responses(..., product_epoch=...)` returns response IDs, scope epochs and original member requests only for the active running product. The engine must commit derived rows through its existing product-epoch fence before `acknowledge(receipt, result_reference=...)`. A crash between row commit and acknowledgement can repeat local consumption, handled by semantic row dedup; it does not repeat a successful checkpointed request. A crash after the supplier response but before durable task completion can still cause a retry. The queue does not claim impossible exactly-once network delivery.

Owner/lease epochs fence stale request completions. Product and scope epochs separately fence publication. New source epochs remain distinct identities. No worker helper reports complete product coverage or complete catalog status simply because a supplied request manifest finishes.

## Explicit coordinator lifecycle

`crawler.harvest_coordinator.HarvestCoordinator` now connects installed manifests to actual queue execution using a caller-supplied transport factory. It leaves application and engine wiring to the caller.

```python
coordinator = HarvestCoordinator(store, transport_factory, workers=3, publish=None)
await coordinator.record_discovery(run_id, product_id, discovery_summary)
await coordinator.install(run_id, product_id, scope, accepted_quote_manifest,
    discovery_summary=completed_discovery_summary)
preflight = await coordinator.start(run_id, measured_rps=measured_source_rate)
status = coordinator.status(run_id)
await coordinator.pause(run_id)
await coordinator.start(run_id, measured_rps=updated_measured_source_rate)
await coordinator.stop()
```

`install` accepts the nested request shape returned by `plan_exact_quote_requests`, or flat source price-table GET entries with full context and explicit `lookup_evidence_id`. `normalize_quote_manifest` rejects unfinished, unaccepted, unresolved, unsupported-route or missing-lookup manifests. It never turns candidate requests into validated products. Discovery progress can be recorded before installation; status retains unknown counts instead of presenting them as zero.

No request runs during construction, discovery recording, manifest installation or status reading. Every currently active product must have an installed manifest and completed discovery before `start`. Products the application has paused are excluded from active execution and remain visible in the overall status. `start` atomically saves the preflight and `harvest_preflight` event, then awaits the optional `publish(run_id, event_type, payload)` callback. Only after publication succeeds does it enable workers. The callback is a broadcast hook; the event is already persisted. With no callback, the durable event is available to the application's existing event feed before workers are enabled.

There is one shared asynchronous pool across every explicitly started run in a coordinator. Starting another run does not create another per-run pool. The supplied ordinary `Transport` remains responsible for the shared source limiter and authentication. External run/product pauses are observed and in-flight work without a remaining active consumer is cancelled. `pause` also provides an explicit application lifecycle hook. `stop` drains/cancels workers; a new coordinator can resume stored manifests only through a new explicit `start`, which republishes preflight before requesting anything.

The read-only status helper combines per-product candidate/resolved/unresolved/validated-base counts, unknown-count product IDs, installed scopes and queue preflight. A drained request manifest is labeled `requests_drained`; `catalog_complete` and `composition_complete` remain false. Consumer row generation, full coverage validation and exports remain separate engine responsibilities.

The expanded offline suite now passes **53 tests**. Coordinator integration includes a real `Transport` using `httpx.MockTransport`: query parameters survive into the stored response URL, the complete request context is durably bound, and a resumed coordinator does not re-fetch its saved successful response. Additional tests block or fail preflight publication and prove that the first quote cannot start early. No supplier call, app/engine edit or live restart was made by these coordinator changes.
